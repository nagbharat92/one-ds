# OneDS Design Rules

Generated from src/design-system/rules.json. Do not edit this file directly.

The decisions behind OneDS components. Approved rules guide new work; candidates are proposals, not requirements.

Button is the first enforced sizing migration. Existing specialized controls and experimental overrides are not yet certified against the system-wide geometry rule.

## Approved Rules

### Build everything from OneDS components

ID: composition.shared-anatomy | Foundations | Required | approved

This is the first authoring rule: every interface must use OneDS components and their named parts. Inspect the library before building. Extend the owning component when a capability is missing; if no suitable component exists, create a reusable tokenized component in the library, document it in the showcase, and consume it. Never duplicate component styling or interaction behavior at a page call site.

Why: OneDS is a self-serving library for agents. Refinements must be made once in the owning component or token and propagate to every consumer.

Exceptions: Plain semantic HTML may carry content inside component slots. Product-specific data and orchestration stay in the page. Neither exception permits a local replacement for a shared visual or interactive pattern. Do not create empty wrappers that add no reusable responsibility.

Decision evidence: Explicitly approved as the most important rule in the September 7, 2026 Rules page componentization request.

Enforcement: Partially automated. Rules-page source checks reject locally styled native elements and raw disclosure/navigation controls. Browser tests verify the shared Accordion and Text tokens. Semantic component ownership still requires review throughout the library.

Tokens: `--text-body-size`, `--text-body-leading`, `--toc-width`, `--toc-sticky-inset`

### Design values come from named tokens

ID: foundations.tokens | Foundations | Required | approved

Use named design tokens for colors, spacing, dimensions, radii, typography, and motion. Reuse the existing scale; change the token source instead of scattering values through markup.

Why: A theme or proportion change should propagate from one place to every consumer.

Exceptions: Runtime measurements may bridge values into CSS custom properties where declarative layout cannot express the behavior. They are not an escape hatch for authored design literals.

Decision evidence: Standing user preference: tokenize by default, never hardcode.

Enforcement: Manual review. Review new markup and token ownership. The focused Button tests check its size-token bindings, not all design literals in the repository.

Tokens: `--spacing`, `--button-height-default`

Implementation: [src/index.css](../src/index.css), [src/components/ui/button.tsx](../src/components/ui/button.tsx)

### Spacing and control geometry follow the 4px grid

ID: geometry.control-grid | Geometry and Spacing | Required | approved

Use multiples of 4 CSS pixels for authored spacing and control heights. Measure the complete border box, including padding and borders. Labelled control widths remain content-driven; icon-only controls are square.

Why: Shared geometry makes controls align predictably without per-instance corrections.

Exceptions: Borders, focus strokes, optical corrections, typography, and derived concentric radii have their own tokens. Content-driven widths, wrapping heights, and continuous experimental geometry need not be multiples of four.

Decision evidence: Approved in the September 7, 2026 sizing discussion, with the explicit exceptions above.

Enforcement: Partially automated. Button geometry is tested in desktop and mobile browsers. Other component families remain subject to review and later migration.

Tokens: `--spacing`, `--button-gap`

Implementation: [src/index.css](../src/index.css), [src/components/ui/button.tsx](../src/components/ui/button.tsx)

### Buttons have two size tiers

ID: controls.button-scale | Controls | Required | approved

Default is 40px and Expressive is 56px, measured including borders. Use size=default or expressive. The icon and icon-expressive counterparts have matching square dimensions. Default uses 20px icons and 16px horizontal padding; Expressive uses 24px icons and 24px horizontal padding. Labelled widths remain content-driven. Large, small, and extra-small sizes are removed, not deprecated aliases.

Why: A labelled action and its icon-only peer align at every named size. Fewer choices make agent-authored interfaces more consistent.

Exceptions: Specialized compositions such as calendar cells, toolbars, and experimental surfaces may currently override Button geometry. These are migration candidates, not alternate public Button sizes; do not copy their overrides into new standalone buttons.

Decision evidence: User approved replacing the earlier three-tier scale with Default 40px and Expressive 56px on September 7, 2026. Search, select, and paragraph typography are separate follow-up decisions.

Enforcement: Automated. TypeScript rejects retired sizes. Design-rule tests check the token scale and API; Playwright checks rendered height, icon parity, canvas coverage, and loading behavior.

Tokens: `--button-height-default`, `--button-height-expressive`, `--button-icon-default`, `--button-icon-expressive`, `--button-padding-default`, `--button-padding-expressive`

Implementation: [src/components/ui/button.tsx](../src/components/ui/button.tsx), [src/components/ui/favicon.tsx](../src/components/ui/favicon.tsx), [src/components/ui/input-group.tsx](../src/components/ui/input-group.tsx)

### Choose ghost or secondary from the local tool context

ID: controls.supporting-actions | Controls | Required | approved

Button has no outline variant. Use ghost for an isolated icon-only action or icon-only ButtonGroup when its local action row has no neighboring outlined controls or mixed tools. Use secondary for supporting buttons, including icon buttons, beside search fields, select/dropdown controls, or other mixed tools so their persistent containers have comparable visual weight. Labelled supporting actions such as Cancel also use secondary. Choose the variant explicitly in the owning composition; do not make Button inspect its surrounding DOM.

Why: Ghost keeps isolated icon tools quiet. Secondary gives actions beside visually substantial controls an equally discoverable container. Context provides a clear replacement rule instead of another overlapping button style.

Exceptions: Primary and destructive intent, links, and persistent selected states retain their semantic treatment. Embedded field affordances such as clear or reveal may remain ghost because the field already supplies a shared container. An outer card border alone is not a neighboring outlined control. An isolated icon-only menu trigger may be ghost; opening its menu does not change the trigger's resting variant. Input, select, Badge, Toggle, and other non-Button outline variants are unaffected.

Decision evidence: User approved removing outline Buttons and defined the icon-only versus mixed-control distinction on September 7, 2026.

Enforcement: Partially automated. TypeScript rejects outline on Button-derived APIs. Source checks reject stale outline Button snippets. Desktop/mobile tests exercise icon-only ghost tools and mixed secondary tools, including search, sorting, add/remove, and disabled states. Choosing the appropriate local composition remains a design review requirement.

Tokens: `--secondary`, `--secondary-foreground`, `--state-layer-hover`, `--state-layer-pressed`

### Icon labels include a tokenized optical correction

ID: geometry.icon-label-optical-spacing | Geometry and Spacing | Required | approved

Icon + label means any of three graphic types: an icon, favicon, or loading spinner with visible text. All three use the same 8px graphic-to-label gap from --graphic-label-gap, including expressive contexts. --button-gap aliases that shared token. Add 4 CSS pixels of padding on the label's outer side opposite the graphic using IconLabel and --icon-label-optical-padding. Icon on the left means label padding on the right; icon on the right means label padding on the left. Optical padding must not increase the 8px gap. Button handles ordinary text, numeric text, simple text spans, and asChild link content. Other compositions reuse the same label part; do not create icon-only exceptions to this terminology.

Why: Optical alignment balances perceived visual weight rather than merely aligning bounding boxes. The graphic's shape and filled area can make mathematically equal spacing appear unequal.

Exceptions: Text-only and icon-only controls receive no correction. A label flanked by graphics on both sides has no free outer edge, so it receives no asymmetric correction. Logical padding follows normal inline order in right-to-left layouts; do not visually reorder the graphic and label with CSS. Preserve base padding, icon size, height, and gap. Rich custom labels expose IconLabel explicitly; custom graphic wrappers expose data-icon or data-slot=spinner. Other existing component families are not automatically restyled by this Button migration.

Decision evidence: User clarified on September 7, 2026 that the 4px correction mirrors opposite the icon and also applies to labelled loading spinners, superseding the earlier right-only interpretation. Optical correction is established terminology in Material's system-icon guidance: https://m2.material.io/design/iconography/system-icons.html. Material 2's contained-button-with-icon spec uses asymmetric 12dp/16dp padding: https://m2.material.io/components/buttons#specs. The exact 4px amount is a OneDS decision.

Enforcement: Partially automated. Desktop/mobile browser checks verify mirrored 4px outer padding, exact width contribution, and an 8px text-to-graphic gap with leading/trailing icons, favicons, and spinners in both Button sizes. Dynamic loading tests check correction entry and removal. Text-only and icon-only geometry is preserved. Other component families adopt IconLabel when implementing new icon-label patterns.

Tokens: `--icon-label-optical-padding`, `--graphic-label-gap`, `--button-gap`

Implementation: [src/components/ui/icon-label.tsx](../src/components/ui/icon-label.tsx), [src/components/ui/button.tsx](../src/components/ui/button.tsx), [src/components/ui/favicon.tsx](../src/components/ui/favicon.tsx), [src/index.css](../src/index.css), [src/showcase/demos/forms.tsx](../src/showcase/demos/forms.tsx)

### Nested rounded surfaces share a corner center

ID: geometry.concentric-corners | Geometry and Spacing | Required | approved

For uniformly nested rounded surfaces, derive the inner radius from the outer radius minus the actual edge-to-edge inset. If the inset contains a border, subtract that border and the padding. Clamp at zero.

Why: Independent radii make the gap swell or pinch around a corner.

Exceptions: The relationship assumes aligned, uniformly inset surfaces. A small object floating in the middle of a larger surface does not share its corner center. Rings and shadows consume no layout space.

Decision evidence: Standing user preference: apply concentric corners by default.

Enforcement: Manual review. Inspect actual nesting and painted boundaries. Existing Concentric experiment tests do not certify every component.

Tokens: `--radius-lg`, `--radius-xl`

Implementation: [src/showcase/experiments/concentric.tsx](../src/showcase/experiments/concentric.tsx), [src/index.css](../src/index.css)

### Growing controls keep a fixed corner radius

ID: geometry.growing-controls | Geometry and Spacing | Required | approved

A growing composer or multiline input must use a fixed radius derived from its resting geometry, not an unbounded pill radius.

Why: An unbounded pill radius grows with height and consumes the text column as the control expands.

Exceptions: Fixed-height single-line buttons and square circular actions may use a pill radius. Uniformly nested controls must still respect the concentric relationship.

Decision evidence: Standing user preference: never use radius-pill on a container that grows.

Enforcement: Manual review. Check the empty and multiline states, not only the resting screenshot.

Implementation: [src/components/ui/ai-composer.tsx](../src/components/ui/ai-composer.tsx), [src/index.css](../src/index.css)

### Text stays in its natural case

ID: typography.natural-case | Typography | Required | approved

Do not transform labels, headings, tags, or eyebrows to uppercase. Establish hierarchy through size, weight, and muted foreground tokens, not all-caps text and wide tracking.

Why: Natural-case text is the deliberate OneDS voice, including small metadata labels.

Exceptions: Preserve genuine acronyms, proper product names, and code identifiers. Do not rewrite them merely to avoid capital letters.

Decision evidence: Standing user preference: never all-caps typography.

Enforcement: Manual review. Inspect visible copy and styling; a blanket uppercase-string checker would incorrectly reject acronyms and code.

Tokens: `--font-weight-medium`

Implementation: [src/components/ui/card.tsx](../src/components/ui/card.tsx), [src/components/ui/page-header.tsx](../src/components/ui/page-header.tsx)

### Motion uses named speed and easing tokens

ID: motion.speed-tokens | Motion | Required | approved

Use shared speed and easing tokens for transitions and animations. Name component aliases by their role and preserve a reduced-motion path.

Why: Related interactions should feel coordinated, and their timing should be tunable centrally.

Exceptions: Intent delays, request timeouts, and simulated loading delays are behavior timers, not motion speeds. Repeating animation cadence may use a dedicated pulse token.

Decision evidence: User-established speed-token convention; current scale lives in the shared stylesheet.

Enforcement: Manual review. Check token use and reduced-motion behavior for each affected interaction.

Tokens: `--speed-swift`, `--speed-gentle`, `--ease-glide`, `--ease-settle`

### Showcase previews have Default and Large tiers

ID: showcase.surface-scale | Composition | Required | approved

Use the Default showcase tier for component pages: the shared app-width PageContent and roomy viewport canvas minimum, matching Concentric. Large uses the application tier with full-width PageContent and the existing application-height canvas. The former small component tier is removed; default and named examples must not fall back to its smaller geometry.

Why: Components need consistent room for comparison and inspection. A shared size policy prevents each showcase page from inventing its own preview dimensions.

Exceptions: Canvas alignment layouts such as start and wide remain available, but standard showcase canvases share the Default minimum. Examples that own their canvas retain their component-defined anatomy and content-driven height. This rule governs the showcase shell, not the dimensions of demonstrated components or general-purpose PageContent variants.

Decision evidence: User approved migrating every small showcase page to the existing default tier while preserving the large AI Chat application preview on September 7, 2026.

Enforcement: Partially automated. The showcase surface type permits only default and application. Desktop/mobile tests compare standard pages with Concentric, check named canvas minimums and preview controls, and verify that AI Chat retains its large application presentation. Component-owned canvas geometry is tested separately.

Tokens: `--canvas-viewport-height`, `--canvas-min-height`, `--showcase-block-preview-height`

### Typography is defined by role, not blanket scaling

ID: typography.role-pairs | Typography | Recommended | candidate

Keep size and line height paired. Separate headings, body, and metadata by role; avoid multiplying every text size when a region becomes expressive.

Why: The Expression Lab uses a deliberate hierarchy rather than a uniform enlargement.

Exceptions: The lab's medium-scale 20/16/14px hierarchy is a reference for equivalent roles, not an approved universal replacement for all component typography.

Decision evidence: README documents the medium Concentric typography reference. Broader adoption still needs approval.

Enforcement: Manual review. Candidate only. Existing lab checks validate the lab, not this proposed system-wide convention.

Tokens: `--expressive-title-size`, `--expressive-body-size`, `--expressive-caption-size`

### Every control keeps its interaction contract

ID: accessibility.control-contract | Accessibility | Recommended | candidate

Reuse native or established primitive behavior. Keep keyboard focus visible, give icon-only controls an accessible name and tooltip, and test disabled, loading, and reduced-motion states.

Why: A visual treatment must not silently remove an existing way to operate the control.

Exceptions: Disabled controls may suppress hover tooltips. Touch target requirements are contextual: a visual control's size alone is not a claim of universal accessibility compliance.

Decision evidence: Button's automatic tooltip behavior and the Radix-based component architecture are existing implementations; this combined authoring checklist is proposed for approval.

Enforcement: Manual review. Candidate wording does not waive accessibility requirements. Automated checks cover selected interactions only; keyboard and assistive-technology review remain necessary.

Tokens: `--ring`
